# Metrics, data and architecture

## Measurement semantics

The report's metric catalog records units, sources and meanings. Missing/unavailable measurements are not proof of zero work.

| Measurement | Interpretation and limits |
| --- | --- |
| Frame interval | Elapsed time between successive measured client frames. Includes pacing and scheduling effects. A long interval is perceptible stutter evidence, not necessarily active CPU work. |
| Render submission / stage wall time | Monotonic elapsed time around the instrumented client/render stage. Can include blocking and nested work; stage durations need not be disjoint or sum to a full frame. These are not GPU timer queries. |
| GPU elapsed timestamps | Optional GPU-clock elapsed time between submitted RenderBefore/RenderDone markers. Includes pipeline bubbles/CPU starvation; excludes earlier game ticks and subsequent present/swap. This is not GPU busy time, utilization or total frame latency. Results arrive asynchronously and are aggregated when read back, so must not be attributed to the CPU frame/window receiving them. |
| FPS and percentiles | Windowed frame rate and distributions. P95/P99 expose tails that averages hide. Percentiles of individual frames differ from percentiles of already averaged windows. |
| CPU one-core percent | `100 × change in Process.TotalProcessorTime / elapsed wall time`. One saturated logical core is about 100%; parallel work can exceed 100%. |
| CPU machine percent | One-core percent divided by the runtime's logical processor count. This is this process's normalized use, not total utilization by every process on the machine. Affinity/container CPU reporting can affect the denominator. |
| Working set / private / managed memory | Different views of process memory. They overlap and must not be added. Managed/GC snapshots do not represent every native allocation or graphics resource. |
| Allocation rate | Change in process-wide cumulative managed allocated bytes over the observation interval. This is allocation pressure, not retained memory or a per-mod allocation bill. |
| GC counts and pause context | Runtime collection/pause observations. Collections, allocation bursts and stalls may correlate; a periodic snapshot cannot establish every pause's exact relation to a particular frame. |
| Thread pool | Runtime thread, pending-work and completed-work counters. They describe the shared process pool. |
| Census and ping context | Client-accessible world/player observations; inspect age, scope and truncation. They do not measure a remote server's total entity/chunk population. |
| Collector duration | Instrumentation cost observed for collection work; does not account for every effect of instrumentation or the external worker. |

## EventPipe is sampled thread activity

`Ember.Trace` runs separately under .NET 10. The mod writes a session request identifying the current client PID and process start time; a standalone supervisor launches bounded EventPipe segment workers to collect runtime events and sampled managed stacks. The supervisor can finish parsing/export after the client exits. Keeping trace parsing and its dependencies outside the game reduces assembly conflicts and avoids performing that work on the render thread; it does not eliminate target-process sampling overhead or system resource contention.

**An EventPipe sample is a thread-stack observation, not an exact on-CPU measurement.** Threads may be observed while waiting. Self samples count observations whose leaf is a frame; inclusive samples count observations containing a frame. Inclusive totals can overlap across callers and cannot be summed as exclusive costs. A method with many samples is a candidate for investigation, not necessarily the consumer of the same percentage of CPU.

The speedscope export uses sample weights and unit `none` to preserve this distinction. Its per-thread profiles are intended for stack exploration; they do not reconstruct a complete scheduler timeline. Allocation events are sampled, not exhaustive object accounting. Lost events, missing stacks, unresolved symbols, limits, short captures and rundown failures reduce confidence. Native/GPU execution is outside this measurement's scope, and per-mod totals are sampled, overlapping observations rather than exact CPU accounting.

Default segments target 60 seconds and retain up to 50,000 observations using bounded sampling. Whole-session merging uses equal-probability segment quotas constrained by the retained/observed ratios, with a global ceiling of 200,000 stack observations, then restores chronological order. Quota rounding can omit sparse segments. Incident stacks are independently selected from segment-retained observations before global downsampling, with bounded pre/during/post quotas. Hotspots count retained thread observations; reservoir omissions are distinct from lost EventPipe events. Additional stack-depth, frame-cardinality, trace-byte and parser-resource limits are reported separately.

Stack coverage is the union of usable trace intervals, not proof of continuous events or uniform sample density. Attachment, segment transitions, rundown, parsing, retries and failures can leave unobserved gaps. Reports carry segment timestamps, status, trace/sample counts, parse durations and errors, plus profile quality/rundown notes. When attachment is denied, a running supervisor can still finalize monitoring-only evidence. Missing stack data must not be interpreted as inactivity.

Known stream truncation or the parser's event-conversion limit can discard a segment's tail. In that case a segment profile records `usableDurationSeconds` separately from nominal `durationSeconds`, using resolved stack events processed before reservoir selection. Completed segment end timestamps and coverage are clipped to this usable prefix; the last randomly retained sample does not define the cutoff. Discarded tail intervals receive no stack-coverage credit.

GPU timestamps use a bounded asynchronous query ring, checking availability before result reads. Unsupported/changed contexts or errors disable timing; ring pressure causes skips. Environment context records availability/status and submitted, completed and skipped counts. This avoids deliberately waiting for query completion, but does not guarantee a fixed driver-call cost.

Microsoft explicitly documents that the former `dotnet-trace collect` profile name `cpu-sampling` was misleading because it sampled threads regardless of CPU use; see [the current profile documentation](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-trace#options). Kernel on-CPU tracing is a different mechanism.

## Inventory and attribution

The report records mod metadata and dependency declarations, loaded systems and assemblies, module identities, and available file SHA-256 hashes. Harmony inventory identifies patched methods, owners, prefixes, postfixes, transpilers and finalizers where discoverable.

`mods[].enabled` records the client loader's enabled state when available. Helper-library ownership is inferred from mod-supplied assembly filenames matched to loaded assemblies; a shared library can list multiple supplying mods. Profile thread IDs are operating-system thread IDs and must not be equated with managed thread IDs in the environment snapshot.

Assembly-to-mod associations help navigate samples. Shared libraries, multiple mods in one assembly, generated methods, cross-mod calls and patches can make ownership ambiguous. Patch presence does not show that a patch was slow, and a mod filename/hash does not show how much work it performed. Use call paths, time-local evidence and controlled reproduction together.

### Assigning sampled frames to mods

`profile.modSamples[]` answers "whose code are these samples" per mod: `selfSamples` counts observations whose executing leaf frame belongs to the mod, `inclusiveSamples` counts observations with the mod anywhere in the stack and therefore overlaps across mods and must not be summed, and `managedSelfSamples` restricts self to observations the runtime classified as managed. `profile.unattributedSelfSamples` is the denominator that matters: observations whose leaf frame belongs to no known mod, which is framework, vanilla or unidentified code rather than an "other mods" bucket. Ownership is a lookup aid, not proof of cause.

A frame's mod comes from the module the runtime named for the sampled address (`profile.frames[].module`), looked up in the assembly-to-mod map the client supplied. When the converted trace lost that association — every managed frame reports TraceEvent's synthetic `ManagedModule` — the parser re-reads the segment's raw trace and rebuilds code-address ranges from its method-load and module rundown events (`framesRecoveredFromRawTrace`). Only when neither source names a module does a frame fall back to the declaring method's root namespace, and only if that namespace matches an assembly a mod declares; such frames are marked `profile.frames[].match: "type-namespace"` so they are never mistaken for the runtime's own answer. `framesWithoutModule` counts frames left unowned. A named vanilla module is an answer and is never overridden by a namespace, so an empty mod list means missing evidence, not absent activity. The profile notes record how much of the attribution came from each source.

## Heap dumps

A heap dump exists only because the player ran `.ember heapdump` during a recording. The game writes a request file, the supervisor consumes it and runs one isolated dump worker, and the result is acknowledged back to chat. A request that cannot be served is refused with a reason and still appears in the report: an omitted request would be indistinguishable from one that was never made.

`SUMMARY.md` carries a **Heap dumps** section listing every request with its status, the managed heap it measured, its largest holder, the trace against the buffer it had to fit in, the hitch it cost the client and what the request cost in stack coverage. When a recording holds more than one completed dump the section also carries a **Change since the previous dump** table: retained bytes are a partition of the heap, so the totals subtract directly and the largest owner changes say where the difference went. A failed or refused request is a row with its reason, and a dump whose totals are lower bounds says so there and appears as a finding. The explanations that apply to every dump in a recording — what a repeated walk means, what a full buffer costs — are recorded once for the recording instead of once per request.

The worker attaches the same way the recording does, captures the CLR GC heap walk, reduces it, and **deletes the raw trace as soon as the aggregate exists**. The raw heap trace is the one artifact of this feature that cannot be redacted usefully, because it is a binary object graph containing every string in the heap; it is therefore never exported, and the report keeps only counts, sizes and module names.

Retained bytes come from a dominator tree over the captured object graph. Attribution is a partition: every reachable byte is assigned to exactly one *holder root* (a dominator child of the virtual root), so the per-owner sizes add up to the heap rather than counting ancestor chains twice. Bytes that no strong root reaches are reported separately and never folded into an owner.

What the numbers mean, and what they do not:

- They show **which owner holds** an object. They do not show why it exists, when it was allocated, or which mod caused it to grow. Confirming a suspicion means changing one thing and repeating the dump.
- Ownership is assembly-based. A shared library, a vanilla type held by a mod, or an object reachable from two mods is attributed to the holder root the GC reports, which can differ from the mod a person would name.
- A dump is one moment. Repeated dumps taken by hand can be compared; nothing is interpolated between them, and there is no continuous memory timeline.
- **New stack segments are held back while the walk is captured; the segment that is already running keeps capturing.** The runtime answers every EventPipe session that attaches while a walk is being captured with a complete walk of the heap, broadcast to every session that asked for one. A session that merely stays attached does not: it measured **0.09%** unattributable against **0.04%** with nothing attached, and a forced blocking gen2 collection every second during the capture changed nothing either — **90** collections landed inside one capture window with one walk, a **19 ms** span and **0.06%** unattributable. Attach cycles therefore make one dump describe the same unchanged heap many times over: a rotating recording produced **4,553,580** walked objects carrying only **303,949** distinct addresses — about **fifteen complete copies** of a heap that never moved. The analysis collapses those copies onto the first walk instead of counting them as more heap, so such a trace describes the heap once (**303,949** objects, **0.13%** unattributable, `complete` true) and reports the walked count it carried; the copies still cost the trace, the capture and the span, which is why the supervisor holds new segments back anyway. What it no longer does is stop the segment that is already capturing: that costs the walk nothing measurable, and stopping it threw away stacks the recording did not have to lose. The hold covers the capture and ends as soon as the walk has been captured — the reduction reads a closed trace and needs no quiet target — and it is published as its own event with its length on the aggregate. Metrics keep journaling throughout and the journal is never interrupted, but the walk itself stops the client while the runtime performs it during a blocking collection: that stop is measured from the recorded frame intervals as `freezeMilliseconds` and is not the walk's span. And because the attached segment keeps running, the held-back interval is not by itself a hole in stack coverage; the session's own segment intervals say whether one fell in it. Measured on the fixture: the hold is the capture (**12.9 s** held for a 12.8 s capture) where the previous design held capture plus reduction (**10.0 s** for a 9.2 s capture and a 0.3 s reduction), and a detach inside the capture does not re-walk the heap — a four-second segment that stopped itself mid-capture left one walk (**303,901** walked, **303,901** described, **0.09%** unattributable) and ran its full interval. On the first client to run the previous design the hold was the whole cost: **305 s of 895 s** of the recording (**34%**) had no new stack capture for four dumps whose walks cost **6.4 s** of span and four freezes of **2.6–3.4 s**. The next client run, which no longer stops the segment that was already capturing, held new capture back for **189.0 s** of a 512.6 s recording and cost **77.3 s** of stack coverage (**15.1%**): **74.8 s** of that gap fell inside the three holds and the rest was segment rotation and the start of the recording, so **59.6%** of the held-back interval was still covered. The split is reported as `uncoveredSeconds`, `uncoveredDuringHeapDumpHoldsSeconds` and `heapDumpHoldSeconds`, because a hold is not a gap and the summary has to say which is which. **The frames still pay for the walk.** A heap walk is performed by the runtime during a collection, and the first real client dump made the client collect: the only two GC pauses above 500 ms in that 138 s recording (**2,099 ms** and **1,467 ms**, both with a gen2 collection) fall inside its parked interval, and they are the two frame hitches of **3.45 s** and **1.53 s** against a 23 ms maximum before the request. Expect a dump to cost a few seconds of hitching, and read the recorded frame intervals rather than the walk span.
- `complete` is three checks, not a quality grade: the node/edge accounting must balance, at most **25%** of the heap may be unreachable from the captured strong roots, and the trace must not have reached the EventPipe buffer it was captured into. They are reported separately because they have different causes: unbalanced accounting means events were dropped, a high unattributable share means the objects and the roots in the trace do not describe the same moment, and a trace at or above **90%** of its cap (`HeapDumpBuffer.Saturated`) means the ring overwrote the oldest events of the walk, which costs exactly the roots and the objects they point at, because a walk emits those first. Measured unattributable shares: **0.00%** for a large coherent synthetic heap, **0.05%** for a live server with nothing else attached to the process, **11%** for a tiny isolated heap (small heaps carry proportionally more infrastructure objects outside the strong roots, which is why the threshold separates a quarter rather than demanding near-zero), **5.9%** / **6.3%** for two dumps taken in one recording with the stack capture parked, **0.09%** for a dump taken with one segment attached for the whole walk against **0.04%** with nothing attached, **0.06%** for a dump with a forced gen2 every second and no session attached at all, **93.3%** for walks captured while segment workers kept attaching before those copies were collapsed (**0.13%** after the collapse, with `walkedNodeCount` **4,553,580** against **303,949** objects), and **62%** for the first real client dump, whose 1,045.6 MiB trace filled the 1024 MiB cap that was then the default. Every dump states its share and its cap in the notes; the aggregate carries `bufferMegabytes` and `walkedNodeCount`. When `complete` is false every size is a lower bound on a partial heap, and when `walkedNodeCount` is above `nodeCount` the trace carried the heap more than once and those copies were collapsed onto the first walk.
- `spanMilliseconds` is the time between the first and last heap-walk event, and it is not a measured suspension. With the target to itself it is one burst (**16-23 ms** on the fixed measurement fixture); a span of seconds means the walk was repeated by sessions attaching during it (**33.2 s** with two-second segments, **75.0 s** with five-second ones). Compare the recorded frame intervals over the same window.
- `freezeMilliseconds`, `freezeStartUtc` and `freezeGcPauseMilliseconds` are that comparison, made once at assembly: the longest completed frame interval that began within **5 s** of the request (250 ms of lead is allowed, because the attach can interrupt a frame already in flight) and the runtime GC pause recorded in the timeline windows it falls in. Measured on one client, three dumps: the interval began **0.101 s**, **0.103 s** and **0.109 s** after the request and lasted **2,345 ms**, **2,806 ms** and **2,818 ms** against a span of **1,465**, **1,376** and **1,416 ms**, with **809**, **1,279** and **1,280 ms** of GC pause in the same windows. The window is deliberately narrow: the same client had two hitches of **1,587 ms** and **1,405 ms** inside those holds, at **+35 s** and **+48 s**, and they were its own collections, so they are not charged to the dump. A recording that kept no frame in the window says the hitch is *unmeasured*, which is not a hitch of zero, and a walk that cost one ordinary frame is measured on the dump without being raised as a finding.
- `deltaSincePrevious` compares each completed dump with the previous completed one in the same recording: `totalBytes`, `attributedBytes`, `unreachableBytes`, `nodeCount` and `rootCount` are differences, `secondsBetween` is capture to capture, `lowerBound` is true when either side is a partial heap, and `holders`/`types` are the largest changes matched by module and by type name (a row that is new or gone carries a zero on the missing side). A refused or failed request measures nothing, so it neither gets a delta nor becomes one.
- A dump that stops before it produces an aggregate records what stopped it, and the buffer is named ahead of the object budget because it is the limit the other cannot substitute for. A saturated buffer has already discarded the walk's oldest events, which are the roots, so raising `heapDumpMaxNodes` alone would analyse a trace with no strong root for most of its objects. The failure text gives the buffer size to raise and still reports the object budget the same walk exceeded; the failed aggregate keeps that text in its notes. The first real client failure hit both limits at once and reported only the object budget, which read as if one knob would fix it. A dump that ran out of time is the third cause and is recorded as its own: `FailureKind` is `time-budget`, the text names the stage the deadline reached, the trace size against its buffer and how many walked objects had been read, and the only limit it sends the reader to is `heapDumpTimeoutSeconds` — which extends the capture and the reduction together. A failed dump carries no heap figures at all, so an interrupted reduction cannot be quoted as a heap; a dump that never settled still marks the event timeline at the moment it ended, because an interval with a request and no outcome reads as a game problem rather than as this dump.
- `nodeCount` counts the objects the aggregate describes — one per distinct address, because the copies of a repeated walk are collapsed onto the first one — and `walkedNodeCount` counts the objects the trace actually carried. The two differ exactly when the runtime answered several attaches with whole walks of the same heap; the difference is what that repetition cost in trace, capture and span, not more heap. `edgeCount` counts references between the described objects, so it pairs with `nodeCount` rather than with the trace.

Allocation figures come from **GC allocation ticks**, the only allocation stream a trace actually contains. The runtime raises one when roughly **100 KB** has been allocated and names the type and size of the object that crossed that boundary, so `allocations` carries the sampled objects' bytes and their sample count, grouped by the assembly that owns the allocated type. Measured on .NET 10.0.12 against a process allocating 1.5M objects in 45 s: **99,411** samples in 3 s, **256.9 MB** of sampled objects against **10.6 GB** actually allocated, with `System.Byte[]` carrying **92%** of the samples. The `GCSampledObjectAllocationHigh|Low` events a dump used to read are never emitted by that runtime — those two keyword bits alone produced a trace of one event (the session metadata), and no event with their ids (20, 32) arrived under any mask, including all 64 bits — so a dump requests neither them nor the .NET 10 `AllocationSampled` event (id 303, EventPipe-only keyword bit `0x0000080000000000`), which carries a type name and an object size per sample but which this TraceEvent version cannot decode. The figures cover the window in which the dump was emitted and drained, carry no call stacks, and are not the retained set.

## Retention and export

Lightweight monitoring uses a recent in-memory buffer: defaults are 900 seconds and 120,000 frame records. `.ember export` snapshots that buffer, including while a session is active. The JSON model calls individual client records `ticks` for shared collector compatibility; `frames.csv` labels their client semantics explicitly.

`.ember start` and no-argument `.ember profile` begin a disk-journaled session. Approximately per-second batches contain runtime windows, individual frames, events/logs and available census/context updates. They are queued to a bounded background writer and flushed to `batches.ndjson` under `<DataPath>/Ember/sessions/<id>/`. Session history is independent of the 15-minute buffer: a 30-minute session needs no history configuration edit. Default limits are four hours and a 2048 MiB working-directory budget, with a separate 512 MiB journal allowance. `.ember profile <seconds>` supplies a 5–28,800-second timer. Stop, world exit, client exit or resource/time limits initiate finalization.

Final assembly retains up to 500,000 individual frames by uniform reservoir sampling across observed journal frames. Incident discovery runs before this frame downsampling. Runtime windows, logs and events have separate 20,000-entry tails, and context history is bounded; very long recordings can therefore omit earlier entries. Notes disclose omissions, dropped batches and incomplete/corrupt lines rather than interpolating missing evidence. Incident stack selections supplement the bounded global profile; neither is an exhaustive execution history.

Request/context files, the saved journal and segment checkpoints support startup recovery and `.ember recover`. Complete usable records can survive a client crash; in-flight batches, incomplete traces or damaged files may not. Recovery retries finalization from saved evidence and is not a perfect crash recorder.

`Ember.Core` contains report models, collection/analysis/export support and the embedded `viewer/report.html` resource. Export creates `GPT-REPORT.md`, structured JSON, summaries, metrics/frame/incident CSVs and a self-contained HTML report, then adds a file-size/SHA-256 manifest and ZIPs the bundle. The manifest lists report payloads; it does not hash itself. A speedscope file is added only when profile data is present.

**`GPT-REPORT.md` is the recommended single-file first attachment for GPT.** It combines selected evidence and interpretation guidance; retain `report.json` for deeper investigation. `llm-context.json`, `SUMMARY.md` and `ASK-AN-LLM.md` remain supplementary context. Selected windows and representative stacks are not substitutes for all retained evidence. Large JSON/HTML payloads and checksums are streamed during export to avoid duplicate report-sized string allocations.

Exports are local under `<DataPath>/Ember/exports/`. `report.html` opens offline without a web server or hosting. The default retention policy keeps 20 matching Ember export ZIPs. Copy a report elsewhere to retain it longer. `OpenFolderWhenFinished=true` asks the desktop to open the export directory after session finalization. Reports are not automatically uploaded.

## Redaction and sharing

`IncludeModConfigs=false` is the default. Optional configuration values pass through redaction if enabled. Diagnostic context may still identify installed mods, assembly/method names, machine/runtime characteristics, user-entered markers, and relevant log content. Redaction is heuristic: review the actual bundle before sharing it, especially if enabling optional configuration capture.

`ASK-AN-LLM.md` accompanies evidence rather than replacing it. Useful analysis should quote observed timestamps/metrics, distinguish observations from hypotheses, account for missing data and process scope, and suggest a reproducible next experiment. A report alone cannot prove which mod must be removed.
